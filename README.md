# Achterhus Telemetry API

FastAPI backend for service-run lifecycle, status, event, and metric telemetry. The
orchestrator registers each run; the containerised service reports application status
updates and events; the dashboard reads paginated run records and service summaries.
The API uses PostgreSQL through SQLAlchemy's asynchronous `asyncpg` driver.

## Local setup

Install the locked development dependencies with `uv`:

```bash
uv sync --locked --all-extras --dev
```

Set `DATABASE_URL` in the API process environment. It must be a PostgreSQL connection
string. For local development, keep credentials in an ignored `.env` file or inject
them through your development environment; do not commit real credentials. An example
with placeholders is:

```dotenv
DATABASE_URL=postgresql+asyncpg://telemetry_app:<password>@localhost:5432/<database>
```

The PostgreSQL role must be able to create tables in the `telemetry` schema, and its
search path must include that schema. The application does not create databases,
schemas, users, or credentials. Supply the connection string through the container
environment in deployment.

Run the API locally:

```bash
uv run uvicorn telemetry.main:app --host 127.0.0.1 --port 8000 --reload
```

The `telemetry-api` command is also available. `HOST` and `PORT` can be used to
configure its bind address and port.

## API

All endpoints are under `/api/v1`.

### Register a run

`POST /runs` is used by the orchestrator to register a run before it is scheduled for
execution. `run_id` is the UUID generated by the orchestrator and supplied to the
container as `SERVICE_RUN_ID`.

```json
{
  "service_name": "newsletter-worker",
  "run_id": "8d4b64d8-7e28-42f8-8cb8-3b4d202d3d83",
  "status": "SCHEDULED",
  "source": "orchestrator",
  "timestamp": "2026-09-29T10:15:00Z"
}
```

The status defaults to `SCHEDULED` and the source to `orchestrator`. Re-registering a
run ID returns `409 Conflict`.

### Update run status

`PATCH /runs/{run_id}/status` records a lifecycle transition and its source and
timestamp. Repeating a non-terminal state is allowed. Attempts to change a terminal
run, or to make an invalid transition, return `422 Unprocessable Entity`.

```json
{
  "status": "CREATE_FAILED",
  "source": "orchestrator",
  "timestamp": "2026-09-29T10:15:00Z",
  "error_details": {
    "reason": "DockerImageNotFound",
    "message": "The required image could not be pulled"
  }
}
```

Optional `metrics` and `logs_summary` fields can also be supplied. Application
failures should use `FAILED`; orchestrator and watchguard failures should use the
corresponding lifecycle status and source.

### Run events

`POST /runs/{run_id}/events` adds a structured, timestamped event. `GET
/runs/{run_id}/events` returns the run's events in timestamp order. An event contains
`event_type`, `source`, `timestamp`, and a JSON object in `details`. Status changes
are also recorded in the event history.

### List runs and overview

`GET /runs` returns a JSON array. It accepts:

- `service_name` and `status` filters;
- `since`, an optional ISO 8601 cutoff timestamp; only runs whose start time (or
  registration time when they have not started) is at or after the cutoff are included;
- `limit`, the page size (default `50`, maximum `200`);
- `page`, a one-based page number (default `1`).

For example, `/api/v1/runs?service_name=newsletter-worker&since=2026-09-29T10:15:00Z&limit=25&page=2`.
`GET /overview` returns the latest status, latest run time, total run count, and
failed-run count for each service. It accepts the same optional `since` cutoff and
calculates each summary from runs at or after that time. The failed-run count includes
application, orchestrator, timeout, and out-of-memory failures.

### Lifecycle statuses

The supported statuses are `SCHEDULED`, `IMAGE_PULLING`, `STARTING`, `INITIALIZING`,
`RUNNING`, `SUCCESS`, `FAILED`, `CREATE_FAILED`, `START_FAILED`, `OOM_KILLED`,
`TIMEOUT`, and `ORCHESTRATOR_ERROR`. `SUCCESS`, `FAILED`, `CREATE_FAILED`,
`START_FAILED`, `OOM_KILLED`, `TIMEOUT`, and `ORCHESTRATOR_ERROR` are terminal.

When a new run reaches `RUNNING`, any older run for the same service still in
`RUNNING` is marked `TIMEOUT` with an API-generated stale-run event.

## Development checks

Run the same quality checks used locally and in CI:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest
```

Unit tests use an in-memory SQLite database; runtime configuration accepts PostgreSQL
only. See [CHANGELOG.md](CHANGELOG.md) for the project history.
